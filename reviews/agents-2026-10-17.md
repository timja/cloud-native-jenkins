The verdict common to the architecture, compatibility and JEP reviews: the idea at the bottom (route `XmlFile` through a versioned key-value store with change events) is sound, but core had gained about 8k lines of cluster policy (the shared queue, running builds and adoption, build snapshots, permalinks, the XML merge, reflective reloads), several of them registered on upstream extension points at a high ordinal, and build data was keyed by path, so a rename cost O(builds). That led to decisions 1 and 2 below and to the **cnj2 re-cut**: the core stack is rebuilt as new `cnj2/*` branches from `fork/cnj/base`, with the engines in the `cluster` plugin behind a few core extension points ([targets/17-architecture.md](../targets/17-architecture.md), API frozen in [targets/17-api.md](../targets/17-api.md)). Bugs found in the old stack were fixed there first (tag `cnj-rev3-final` = `0a47f66bc6` carries them) so that the port starts from fixed code.

**135 findings** (a row each below; a few rows group a JEP's minors): 42 fixed (on the old stack, in the cluster plugin, on the standalone PR branches or in the JEPs), 1 partly fixed, 40 resolved by the cnj2 design or a decision, 12 documented, 36 open and carried into the cnj2 port, 4 not changed. A row with two outcomes is counted by its first.

Outcomes: **fixed** · **by design** (cnj2 removes the code or the cause, or a decision below settles it) · **documented** (JEP text or javadoc) · **open → cnj2** (to be done in the named cnj2 branch or plugin step; the port agents have the findings) · **not changed** (ready as is, or a nit not worth the change).

## Decisions, 2026-10-17

1. **Architecture: cluster engines out of core.** Core keeps mechanisms (the key-value SPI, routing, `XmlFile`, item lifecycle, the applier for configuration, and small hooks); the shared queue, build records, running builds, item files, the merge and the reload move to the `cluster` plugin, behind three new core extension points (`ExternalBuilds`, `BuildRecordSource`, `StoredConfigReconciler`), one Beta queue API (the hand-off), and `SharedFiles`. No core `@Extension` wraps an upstream extension point.
2. **Build data keyed by item identity, not by path.** Records, placeholders, leases, deliveries and blobs live under `_items/<uuid>` and `items/<uuid>`. A rename moves only configuration, in one store operation with preconditions; blobs never move.
3. **Queue future.** When another controller takes a queue item, the local item is not cancelled: it leaves as taken elsewhere (`LeftItem.isTakenElsewhere()`), its `QueueTaskFuture` stays pending, starts when the remote build starts, and completes with its result; it is cancelled only if the remote item is. Consumers (the CLI's `build -s`, pipeline-build-step) use this path instead of special cases.
4. **Conflict policy.** On a conflicting save, merge the local change onto the stored version three ways; if that is not safe (same part changed on both sides, no base, the key deleted meanwhile, the merge fails), refuse the save and reload the stored version. Never last-writer-wins. This is the only behaviour; `warn` and `strict-ui` are gone.
5. **Sign-out.** Signing out ends the sign-in on every controller, remember-me cookie included, without signing the user out of their other browsers: a per-login revocation entry in the store, checked on every controller and kept until the token's expiry (core `LoginRevocation`).
6. **SSH (outbound) agents: a launch lease.** Exactly one controller connects each outbound static node; the others refuse to launch it and forward its pages to the holder; the lease lapses with the holder's membership. Approved on DESIGN-17 §5.
7. **lockable-resources and pipeline-build-step get small extension points** (`LockCoordinator`, `BuildTriggerRelay`), and the store-facing cluster code moves to the `cluster` plugin, so neither plugin needs a new core baseline.
8. **Cron ticks.** A tick missed because its owner was down or not ready is run by another controller: only ready members own triggers, and the new owner runs each trigger whose tick was due and not claimed since, once (coalesced), within a bounded window. A tick still never runs twice.

Approved on DESIGN-17, same day: re-cut the core stack as `cnj2/*` and close timja/jenkins #139–#162 once the new PRs are up; the launch lease (6); **no migration of stored data** (the old store layout is refused; stores are wiped).

## Security

These weaknesses were introduced by the stack, so they were fixed or designed out like any other bug:
- **Paths from store keys.** A name in the store such as `..` could be loaded as an item, and a change applied from elsewhere could name a node or user directory outside its parent and delete it (core C, C11). Store names that are no file names are skipped when listing items, the applier ignores any key (or moved-from key) with an unsafe segment, `Nodes` and `User` validate the name before applying or deleting, and sub-item walks skip unsafe names. JEP-250 states the rule.
- **Sign-out.** With the chart's `alwaysRemember`, every sign-in became a remember-me cookie, and signing out did not end it on the other controllers (JEP sponsor M3, JEPs vs code M15). Decision 5; core `LoginRevocation` in B4.
- **The forwarding loop guard** `X-Jenkins-Cluster-Forwarded-From` could be set by a client to stop a request being forwarded (JEP sponsor M3). It now carries the controller's name, a time and an HMAC under a key shared through the store, and a client's own header is dropped (cluster-plugin `67c9e63`).
- **Protected password token** (core C, C15): with the shared `Protector` key the stack introduced, the hidden form field carries an encryption of the password hash under a long-lived key. Replay was already neutralised; the suggestion (protect an HMAC or a nonce, not the hash) is open → cnj2 B4.
- **A lost build appending to the log** of the new owner, on S3 and Azure (JEPs vs code M1), and **a fenced owner writing over the new owner's record** through a check-then-write `writeIfHeld` default (M3): fixed (below).

## Design questions

1. **Moving an item's blobs is not atomic with the destination check** (4271575725, #145).
   - **Now:** `PersistenceStores.move` checks the destination, then moves the blobs, then the entries. A controller creating the same destination in between can lose its blobs, and the rollback can drag them to the source.
   - **Options:** (a) claim the destination first with a create-only marker entry in the store, then move blobs and entries, then drop the marker; (b) a conditional `BlobStore.move` that fails if the destination exists (Azure and S3 can do conditional writes, but not a conditional move of a prefix); (c) narrow it: roll back only the blob keys this call moved.
   - **I'd suggest** (a); it needs no SPI change.
2. **Publishing is not fenced by the lease** (4271560430, #149).
   - **Now:** a controller checks it still holds the build's lease, then uploads the snapshot and writes the record. A lease taken over during the upload does not stop the stale write. The epoch is called a fencing token, but no store write checks it.
   - **Options:** (a) an SPI fenced write, e.g. `write(key, bytes, version, leaseKey, epoch)` that the store applies only while the lease holds that epoch (one transaction in Postgres); (b) re-check `holds` after writing, and delete or roll back on loss. (b) narrows the window but doesn't close it.
   - **I'd suggest** (a), as it's cheap in Postgres; the question is whether core's SPI should grow it now.
3. **Store I/O under the queue lock** (4271593279, 4271593600, 4271593383; #150).
   - **Now:** publishing a waiting item, the start gate (`get`, `claim`, lease acquire) and folding all call the store while holding the queue lock, so a slow store stalls the queue. Folds are read-modify-write, so two at once can lose a cause (attribution only, never a duplicate build).
   - **Options:** an outbox for publishing after the lock, plus an in-memory view of records fed by the subscription, so the gate decides from memory and claims asynchronously. And a store-side fold (merge causes, take the minimum due time) or a versioned compare-and-set update.
   - **This is the biggest change here:** worth a target of its own? So far the prototype assumes a fast store, which held in ET16/ET17.
4. **`PersistenceStore.move` returns nothing** (4271545416, #141).
   - **Now:** after a move, `PersistenceStores` re-reads the moved entries to learn their new versions. Another controller writing in between is then taken as known, and overwritten.
   - **Should** `move` return the new versions (an SPI change: cluster-postgresql's `move` would return them), or is the re-read enough for now?
5. **Links to builds running elsewhere need owner routing** (4271604507/4271604562, #160).
   - **Now:** in core alone they 404 until the build completes; the cluster plugin's `OwnerRoutingFilter` answers them.
   - **Should** core render plain text unless a router says it routes (a small hook), or is "documented, the plugin routes" enough?
6. **REST API typing of local and remote builds** (4271594416, 4271594549, #161).
   - **Now:** `Job.getBuilds()`/`getAllBuilds()`/`getLastBuild()` are typed `Object` to mix in `RemoteBuild`, which makes `/api/schema` untyped. Data is unchanged, since Stapler serialises by runtime class. Remote builds now list their actions as empty.
   - **Options:** a common exported supertype (interface) of `Run` and `RemoteBuild`; or keep `Run`-typed getters and add remote builds under a separate property. Separately, the placeholder could record parameters and causes at start, so remote builds list them.
   - **I'd suggest** a separate property: the least surprise for API clients.
